# React 운영 화면

기존 Python 계산·검산 코드를 유지하고 React + TypeScript + Vite 화면을 추가했다.
Streamlit 진입점도 그대로 사용할 수 있다. 실제 제어·입찰·새 운영계획 생성 API는 구현하지 않는다.

## Docker로 실행

Docker Desktop(또는 Docker Engine + Compose)을 설치하고 실행한다. 프로젝트 루트에서:

```bash
docker compose up
```

브라우저: **http://localhost:8000/dashboard/**. 컨테이너 하나가 빌드된 React 화면과
FastAPI를 함께 제공한다. 첫 실행에는 인터넷 연결과 이미지·패키지 다운로드 시간이 필요하며,
호스트의 Python·Node·가상환경은 사용하지 않는다. 기본 접속은 해당 컴퓨터에서만 가능하다.
Docker Desktop의 `8000:8000` 링크나 `http://localhost:8000/`로 열어도
`/dashboard/`로 자동 이동한다.

팀원이 준비할 폴더는 아래와 같다. 개인 사용자 이름·드라이브 위치는 설정에 넣지 않는다.
`data/`, `artifacts/`, `config/`, `docs/results/` 디렉터리가 모두 있어야 실행된다.
예측 원본이 없는 조회 전용 시연에서도 `artifacts/` 디렉터리는 만들어 둔다.

| 위치 | 공유할 내용 |
|---|---|
| `data/processed/distribution_replay/` | 시연할 설비의 결과 폴더 전체: `manifest.json`과 그 파일이 가리키는 시간별 Parquet. 파일명·해시를 보존한다. |
| `data/processed/operator_pipeline/` | 포트폴리오 조회 시 `status.json`과 그 결과의 `backtests/` 폴더. 기존 계산 환경까지 공유하려면 `plans/`, `snapshots/`, `releases/`도 포함한다. |
| `docs/results/` | `distribution_ess_operating_20261115.csv`, `distribution_ess_sizing_20261115.csv`, `distribution_ess_economics_20261115.md` |
| `artifacts/`, 나머지 `data/` | 팀이 공유한 기존 예측·시장 자료를 같은 하위 폴더에 둔다. React 저장 결과 조회에는 모델 재학습이 필요하지 않다. |
| `config/` | 저장소의 설정 파일. Compose가 같은 위치를 연결한다. |

Git에 없는 데이터·결과 CSV·Parquet은 팀 Drive에서 별도로 받아야 한다. 저장소를 복제하는
것만으로 공유 데이터가 다운로드되지는 않는다. 원본 예측만 있고 시간별 결과가 없으면
운영 재생이 활성화되지 않으므로 시연용 **저장 결과도** 함께 전달한다.

Compose는 호스트의 위 폴더를 컨테이너의 `/app/` 아래에 읽기 전용으로 연결한다.
프로젝트 전체를 `/app`에 덮어 마운트하지 않아 이미지의 `frontend/dist`가 가려지지 않는다.
종료·재생성해도 공유 데이터가 유지되며 API는 학습·최적화·파일 변경을 하지 않는다.

- 종료: 실행 터미널에서 `Ctrl+C`, 또는 다른 터미널에서 `docker compose down`.
- 백그라운드 실행: `docker compose up -d`; 로그: `docker compose logs -f dashboard`.
- 코드 변경 반영: `docker compose up --build`.
- 상태 확인: `docker compose ps`, `http://localhost:8000/health`.
- 8000 포트 사용 중이면 프로젝트 `.env`에 `VPP_DASHBOARD_PORT=8001`을 추가하고 재실행한다.
  접속 주소도 `http://localhost:8001/dashboard/`로 바뀐다. 기본 실행에는 `.env`가 필요 없다.

### 공유 결과 경로

새 운영 파이프라인 release/status의 `backtest`, `plan`, `inputs`, `source_paths`,
`output_hashes`와 누락 파일 경로는 프로젝트 기준 상대경로(`/` 구분자)로 저장한다.
예: `data/processed/operator_pipeline/backtests/<결과ID>`.
화면과 캐시 검증은 현재 프로젝트 루트를 기준으로 경로를 해석한다.

기존 Mac/Linux/Windows 절대경로는 알려진 프로젝트 하위 폴더(`data/processed/` 등)를
기준으로 읽을 때 자동 연결한다. 사용자별 경로 치환이나 원본 파일 수정이 필요 없다.
프로젝트 밖 경로·상위 폴더 이동·외부 심볼릭 링크는 허용하지 않는다.
결과 파일 내부의 계산 당시 출처 기록은 해시 검증을 위해 그대로 보존한다.

## Python·Node로 직접 실행

프로젝트 루트에서 Python 환경을 활성화한 다음 실행한다. Node 20.19+ 또는 22.12+가 필요하다.

```bash
npm --prefix frontend ci
npm --prefix frontend run build
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

브라우저: `http://127.0.0.1:8000/dashboard/`

화면 개발 시에는 API 서버와 별도 터미널에서 `npm --prefix frontend run dev`를 실행한다.
`http://127.0.0.1:5173/dashboard/`에서 `/api` 요청을 로컬 8000 포트로 전달한다.
배포용 정적 파일은 API 시작 시 마운트하므로 빌드 후 API를 재시작한다.

## 화면과 상태

- 첫 방문은 `처음 오셨나요? → 설비·사업성 검토 → 선택안 확정 → 운영계획`으로 시작한다. 별도 화면을 중복 구현하지 않고 기존 설비 비교 화면을 신규 고객 모드로 재사용한다.
- 기본 목록은 `운영 시연 가능`이다. 신규 고객은 고정 상한 2.50 MW의 국내 구축비 예시/BNEF 2025, 2 MW / 8 MWh 두 후보가 비교 대상으로 펼쳐지며 최종 선택은 비워둔다. `전체 후보`에서 기존 후보를 모두 확인할 수 있고, `기본 시연 비교`로 기본 선로·후보 비교를 다시 불러온다. 필터에 숨겨진 후보는 비교·최종 선택에서도 해제한다.
- 설비 목록 맨 왼쪽에서 최대 2개 후보를 체크하고, 아래 비교표에서 출력·용량·연간 수입·NPV·운영 결과 연결 여부를 비교한 다음 최종 대상 하나를 선택한다. 선로 변경 시 비교와 최종 선택을 초기화한다. 시간별 결과가 없는 후보도 검토할 수 있지만 운영계획 이동 버튼은 비활성화하며 버튼 바로 위에 이유와 다음 행동을 안내한다.
- `이 설비로 운영계획 시작`으로 선택한 후보·기준일을 이 브라우저에 기억한다. 다음에 기본 주소로 방문하면 같은 후보의 운영계획을 연다. 직접 `#/welcome`으로 이동하면 첫 안내를 다시 볼 수 있다.
- 실제 계정·로그인·서버 저장은 추가하지 않았다. 저장된 선택이 없는 경우 `기존 고객으로 시연하기`는 예시 설비로 진입한다. localStorage가 차단되어도 현재 세션은 계속 사용할 수 있고 재방문 시 복원할 수 없음을 안내한다.
- 운영 현황 → 같은 시간 운영계획 검토 → 결과 재생 → 실적·정산이 동일한 설비·날짜·결과 ID를 사용한다.
- 운영 화면의 `추가 사업 검토` 배너·상단 링크와 실적 화면의 재점검 버튼으로 별도 설비 화면에 진입한다. 비교만 하거나 돌아오면 기존 운영 대상을 유지한다.
- 설비 화면의 `운영결과로 이동`은 저장 결과의 조회 대상 전환이다. 실제 설치·설비 채택·운영 설정을 변경하지 않는다.
- 계획 검토 메모는 결과 ID별 브라우저 localStorage에 저장된다. 서버 공유 기록이나 입찰 확정이 아니다.
- 21곳 포트폴리오와 태양광 5.7 MW 배전망 시나리오는 별도 범위이며 수입을 합치지 않는다.
- 실행이 없는 경우 실제 공급·실행 수입은 null이다. 배전망 VPP 배분 기준의 계획 수입은 저장되지 않았으므로 계획 대비 수입 차이도 미계산이다.

`src/pages/`는 업무별 화면, `components/`는 타임라인·수치·작업 목록, `hooks/`는 요청·메모·경로,
`lib/workspace.ts`는 공유 선택과 재생 상태다. 화면 상태는 [React reducer](https://react.dev/learn/managing-state)로 모으고,
데이터 요청은 키와 AbortController로 이전 설비의 응답이 새 화면을 덮지 않게 한다.
날짜나 설비를 바꾸면 재생을 중단한다. 브라우저 뒤로 가기는 해시 경로를 사용한다.
`Welcome.tsx`는 첫 안내, `Resources.tsx`는 신규/추가 검토 공통 화면, `lib/customer.ts`는 선택 저장·복원·유효성 확인을 담당한다.
서버 API, Python 계산 코드, 의존성은 첫 방문 흐름 수정에서 변경하지 않았다. 선택 확정은 시연의 조회 기준 설정이며 실제 사업 계약이나 새 계획 계산이 아니다.

## 현재 데이터로 진행하는 4–5분 시연

1. `/dashboard/#/welcome`에서 시작한다. “처음 이용하는 중개사업자는 사업에 맞는 설비부터 검토합니다.”
2. `설비·사업성 검토 시작`을 누른다. 기본 선로는 **고정 상한 2.50 MW**이고 비교할 두 설비가 미리 펼쳐진다. 국내 구축비 예시는 연간 VPP 수입 약 **1.76억 원**, NPV **−1.50억 원**; BNEF 2025는 약 **1.84억 원**, NPV **9.00억 원**이다. “출력과 용량이 같아도 배터리·비용 가정에 따라 사업성 결과가 달라집니다.” 연간 수입과 20년 NPV를 같은 기간의 지표처럼 설명하지 않는다.
3. BNEF 2025의 `이 설비 선택` → `이 설비로 운영계획 시작`을 누른다. 운영일은 **2025-05-01**로 연결된다. “검토한 설비 조건으로 하루 운영 내용을 확인하겠습니다.”
4. 계획 화면에서 `확인할 시간`을 **13:00**으로 옮긴다. 공급계획 **2.50 MWh**, 충전계획 약 **0.18 MWh**, 계획 SOC **90%**를 확인한다. 메모 기록은 선택 사항이며 `검토 완료 기록` 후 `운영 현황에서 결과 재생` 또는 상단 `운영 현황`으로 이동한다.
5. 현황에서 같은 13시의 실행 공급 약 **0.39 MWh**, 공급 부족 약 **2.11 MWh**, 실행 SOC **10%**를 확인한다. 필요하면 시간대를 바꾸거나 결과를 재생한다. 최대 공급 부족은 **15시 약 2.47 MWh**다. “계획과 실행의 차이가 생긴 시간을 찾아 계획과 잔량을 함께 확인합니다.” 새 대응안을 계산·실행했다는 설명은 하지 않는다.
6. `실적 보기`로 이동한다. 이날 VPP 귀속 수입 약 **113.9만 원**의 구성인 ESS 귀속 에너지 수입 약 **122.2만 원**, 태양광 용량정산금 약 **2.0만 원**, 임밸런스 페널티 약 **−10.4만 원**을 설명한다. 투자·유지·교체비 차감 전 수입이며, 저장된 백테스트 결과다. 두 기본 후보의 이날 수입은 같으므로 이 하루를 근거로 후보 간 수익 개선을 주장하지 않는다.
7. 마지막에 `추가 사업 검토` 배너로 돌아와 “운영 중에도 다른 설비의 사업성을 별도로 검토할 수 있습니다.”라고 마무리한다. `전체 후보`는 확장 검토를 보여줄 때만 열고, 본 시연은 준비된 후보로 진행한다.

현재 **계획 기준 VPP 수입은 저장되지 않아 계획 대비 금액 차이는 미계산**이다. 시연의 핵심은 사업성 비교 → 선택 → 물리량의 계획/실행 편차 → 실제 저장된 수입 구성 추적이다. 새 예측·재최적화, 실제 설비 제어, 실시간 정산 시연은 포함하지 않는다.

## API와 검증

- `GET /api/v1/dashboard/catalog`: 포트폴리오 결과 묶음, 설비 후보, 저장 결과의 검증 통과 여부. `hasArchive`는 파일 존재만으로 참이 되지 않으며 기존 `load_archive` 검증을 통과해야 한다. 파일이 있어도 검증에 실패하면 `archiveIssue`에 이유를 담고 전체 후보에 유지한다.
- `GET /api/v1/dashboard/snapshot?source=distribution&selection=...&day=2025-05-01`: 하루 계획·실행·수입과 선택일까지의 누적 값.
- `source=portfolio`의 selection은 파이프라인 status.json에 기록된 release ID다.

포트폴리오는 기존 `load_experiment`, `replay_payload`, `plan_revenue_breakdown`을 사용한다.
배전망은 최신 저장 아카이브의 파일 해시·용량·시간 연속성·SOC·연간 보고값·귀속 수입 항목 합계를 검증한다.
손상된 최신 아카이브를 이전 파일로 자동 대체하지 않는다. 연간 값으로 시간별 값을 만들어내지 않는다.
시연 점검 당시 저장 파일이 있던 4개 조합 중 동적 상한 2.50 MW의 사용후 배터리 4 MW / 20 MWh 후보는 최신 저장 파일의 ESS 용량이 달라 검증에 실패했다. 기본 시연 가능 목록은 검증을 통과한 3개 조합이다. 원본 데이터나 계산 코드는 변경하지 않았으며, 문제가 해결되면 다음 목록 조회에서 다시 시연 가능으로 분류한다.

아카이브는 **계산 당시 코드와 입력의 과거 결과**다. 현재 코드와 일치하는 캐시임을 보장하는
기존 `distribution_replay.load`와 용도가 다르며, React 화면과 API에도 과거 결과임을 명시한다.
검토 중 변경된 현재 설정을 아카이브에 소급 적용하거나 자동으로 연간 계산을 시작하지 않는다.
시간별 결과가 없으면 기존 `python -m dashboard.distribution_replay --candidate '후보 ID'`로 생성해야 한다.

테스트용 독립 체크아웃은 `VPP_PROJECT_ROOT=/원본/프로젝트`로 데이터 위치를 지정할 수 있다.
API는 조회만 수행하며 해당 위치에 파일을 쓰지 않는다.

```bash
npm --prefix frontend test
npm --prefix frontend run build
pytest tests/test_react_dashboard_api.py tests/test_api.py tests/test_operator_simulation.py tests/test_distribution_replay.py
```
